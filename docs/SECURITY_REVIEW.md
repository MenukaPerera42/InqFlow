## Application controls and limits

- **Authentication:** bcrypt hashes seeded passwords; login has generic credential errors and a process-local 20-per-15-minute IP limit. API tests cover valid/invalid login, rate limiting, session regeneration, logout, and revoked cookies. Multi-instance limits need shared infrastructure before scaled deployment.
- **Sessions:** PostgreSQL store, signed opaque IDs, HttpOnly/SameSite=Lax cookie, eight-hour fixed lifetime, Secure in production. Secret rotation accepts previous values. The API does not trust proxy headers; production requires direct HTTPS until a proxy topology is reviewed.
- **CSRF/CORS:** Exact configured frontend origins receive credentialed CORS. Unsafe methods require an approved browser Origin, including login/logout and PATCH. Tests cover missing/invalid/allowed origins and preflight. This assumes same-site browser hosting; a different site needs a new cookie and CSRF review. Non-browser clients can forge Origin but still need credentials.
- **Authorization:** Every inquiry query is owner-scoped in Prisma; missing and inaccessible rows share 404. Input schemas reject client-supplied owner, status, and version on creation. Tests use two distinct staff accounts and check list, search, detail, and update isolation.
- **Validation/errors:** Zod bounds fields and filters; JSON body size is 16 KB. Malformed JSON returns 400, oversized JSON returns 413, and unexpected failures return a generic 500 without stack traces. The UI stores no password/session value in browser storage and does not render untrusted HTML.
- **Concurrency:** A status update checks ID, owner, current status, and version atomically and increments the version once. Competing-request integration and two-tab browser tests confirm stale requests cannot overwrite newer status.

## Remaining security actions

Before any production deployment, review and update the two advisory chains, validate the deployment's HTTPS/proxy/cookie/CSRF topology, provision secrets outside local `.env`, and replace the process-local login limiter if running multiple API instances. These are deployment blockers, not evidence of an exploitable request path in the verified local setup.

## Phase 03 authorization review

Protected requests reload current role and account state from PostgreSQL. Team list and detail queries constrain rows by current membership or explicit manager assignment; inactive teams are excluded for non-admin users. Manager inquiry reads require both an explicit active team link on the inquiry and current manager authority. Status mutation retains creator/admin checks, so read access does not grant workflow powers. User, team, category, membership, and manager writes are ADMIN-only, validate strict request shapes, and write a separate audit row in the same transaction. Role changes revoke the affected user's sessions; team authority removal takes effect on the next query without revoking unrelated sessions. A database advisory lock protects the last-admin demotion check under concurrency. PostgreSQL unique indexes cover case-insensitive team/category names and composite membership/manager keys. Remaining operational risks include process-local rate limits and deployment-specific cookie/proxy policy.
